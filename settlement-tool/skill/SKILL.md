# 하이포스 업체 정산 자동화

춘천지역먹거리직매장(사용자)이 하이포스에서 매달 뽑는 "전산원본" 엑셀 한 장으로,
출하업체(약 50~60곳) 정산에 필요한 문서 두 종류를 자동으로 만든다.

- **결과물1** — 정산 총액 증빙 요약표. 사용자가 4년째 써온 고정 양식이므로
  컬럼 구성·순서를 절대 바꾸지 않는다. 결과물1은 그 자체로 증빙자료이자,
  결과물3을 만드는 기초 데이터이기도 하다.
- **결과물3** — 업체별로 세금계산서 발행을 요청하는 표. 화면 일부를 캡처해서
  업체 메일에 그대로 첨부하는 용도라서, 업체 1곳당 표 블록이 세로로 이어지는
  형태를 유지한다. 맨 위에는 결과물3 안 소계 합계와 결과물1 총계가 서로
  맞는지 수식으로 바로 보여주는 검산 섹션이 있다 (아래 참고).
- **출하내역서 스캔 파일명 정리** (`rename_jpegs.py`) — 하이포스에서 자동
  출력해 스캔한 출하내역서 JPEG를 업체별로 정리해서 이메일에 바로 첨부할 수
  있게 파일명을 바꾼다. 자세한 내용은 "출하내역서 스캔 파일명 자동 정리"
  절 참고.

이 스킬은 실제 하이포스 파일(전산원본 + 기존 결과물1/결과물3 예시) 4개를 놓고
사용자와 함께 검증하며 만들어졌다. 아래 규칙들은 전부 그 검증 과정에서 나온
결론이니 임의로 바꾸지 말고, 바꿔야 할 이유가 생기면 사용자에게 먼저 확인한다.

## 실행 순서

1. **이번 달 전산원본 파일을 받는다.** 사용자가 이미 첨부했다면 그걸 쓰고,
   없다면 요청한다. 시트명은 `수수료매출내역(거래처별)`로 고정되어 있어야
   스크립트가 읽을 수 있다 (하이포스 내보내기 기본값이라 보통 문제없다).

2. **작성일자와 직매장 대표자명을 확인한다.** 결과물3의 안내문구에 들어가는
   두 값이다.
   - **출하내역서 스캔 zip이 이미 있다면(전산원본과 같이 왔거나 이미 받아둔
     경우), 작성일자를 사용자에게 묻지 않는다.** 먼저 "출하내역서 스캔
     파일명 자동 정리" 절의 `rename_jpegs.py`부터 돌린다. `--date`를
     안 줘도 각 스캔 상단의 "매출기간 : 2026년07월01일 ~ 2026년07월31일"
     같은 문구에서 종료일을 자동으로 읽어 작성일자로 쓰고, 실행 로그에
     `작성일자 자동 감지: 7월 31일 (...)` 그리고 마지막에
     `작성일자(최종): 7월 31일`을 찍는다. 이 값을 4번 결과물3 생성에
     그대로 쓴다. (로그에 "경고: ... 인식하지 못해" 가 뜨면 그때만
     사용자에게 물어본다.)
   - **zip이 아직 없다면**, 기존처럼 "이번 달 작성일자(예: 8월 31일)와
     직매장 대표자명을 알려주세요"라고 물어본다.
   - 대표자명은 스캔에서 자동으로 읽지 않으므로 위 두 경우 모두 사용자
     확인이 필요하다 (이미 알고 있으면 재사용해도 된다).

3. **결과물1을 생성한다.**
   ```
   python scripts/generate_report1.py <전산원본.xls> <출력경로>/결과물1_M월_매출정리.xlsx
   ```

4. **결과물3을 생성한다.** (결과물1의 출력 파일을 입력으로 받는다) 2번에서
   확정한 작성일자/대표자명을 인자로 바로 넘긴다 — 생략하면 플레이스홀더
   ("7월 31일" / "대표자명 입력")로 채워지므로 반드시 넘긴다.
   ```
   python scripts/generate_report3.py <결과물1_M월_매출정리.xlsx> <출력경로>/결과물3_M월_세금계산서요청.xlsx "<작성일자>" "<대표자명>"
   ```
   생성 직후 `generate_report3.py`가 실행 로그에 찍는 "N개 업체 블록"의 N이
   결과물1의 실제 업체 수(하이포스 합계행 제외)와 같은지 확인한다.

5. **두 파일을 사용자에게 전달한다.** `SendUserFile` 등 파일 전달 도구가
   있으면 그걸로 보내고, 결과물3의 작성일자(B1)/대표자명(B2) 칸은 필요하면
   엑셀에서 바로 고칠 수 있다는 점을 알려준다. 결과물3 상단 검산 섹션이
   "일치"로 나오는지도 같이 확인해서 알려준다.

6. **전산원본과 함께(또는 나중에라도) 출하내역서 스캔 zip을 받았다면
   바로 `rename_jpegs.py`를 돌린다.** "이 이미지를 어떻게 쓸까요?" 같은
   질문은 하지 않는다 — zip을 준 이유는 항상 하나, 업체명으로 파일명을
   바꿔서 메일 첨부용으로 쓰려는 것뿐이다 (자세한 내용은 "출하내역서
   스캔 파일명 자동 정리" 절). zip을 전산원본과 같이 받았다면 이미 2번에서
   먼저 돌렸을 것이므로 다시 돌릴 필요 없다 — zip이 report1/3 생성 이후에
   뒤늦게 왔을 때만 여기서 실행한다. `--date`는 생략해서 자동 인식에
   맡기거나(2번 참고), 이미 확정된 작성일자가 있으면 그대로 넘긴다. 결과
   zip과 매칭결과표를 결과물1/3과 함께 전달한다.

의존성: `pandas`, `openpyxl`, (하이포스 원본이 구버전 `.xls`면) `xlrd`.
세 패키지가 없으면 `pip install pandas openpyxl xlrd`로 설치한다.

## 반드시 지켜야 할 두 가지 계산 규칙

이 두 규칙은 사용자와 함께 실제 데이터로 검산해서 확정한 것이다. 이유를
모르고 지나치면 다음에 스크립트를 고칠 때 실수로 되돌리기 쉬우니 왜
이렇게 하는지 적어둔다.

### 1. 과세공급가액/부가세는 하이포스 값을 그대로 베끼지 않고, 과세지급액(총액) 기준으로 역산한다

하이포스 원본은 공급가액과 부가세를 각각 따로 반올림해서 저장하는데, 이
둘을 그냥 합치면 가끔 총액(과세지급액)과 1원이 어긋난다. 실제로 "재헌식품"
사례에서 원본은 공급가액 1,482,136 / 부가세 148,214였는데, 사용자가 예전에
받은 결과물1에는 1,482,137 / 148,213로 되어 있었다 — 총액은 똑같이
1,630,350인데 내부 배분만 1원 흔들린 것이다.

그래서 `generate_report1.py`는 공급가액/부가세를 원본에서 복사하지 않고,
**과세지급액(총액)을 유일한 기준값**으로 삼아 매번 똑같이 계산한다.

```python
supply = round(taxed_total / 1.1)      # 과세공급가액
vat = taxed_total - supply             # 부가세 = 총액 - 공급가액
```

이렇게 하면 총액은 항상 원본과 정확히 일치하면서, 공급가액/부가세 배분은
매번 같은 규칙으로 결정되어 흔들리지 않는다.

### 2. 하이포스가 붙이는 합계행은 결과물1엔 남기고, 결과물3에선 제외한다

전산원본 맨 마지막 줄은 실제 업체가 아니라 하이포스가 자동으로 붙이는
합계행이다. 코드와 사업자번호 칸이 비어 있고, **거래처명 칸에 업체 이름
대신 업체 수(예: "57")가 숫자로 들어가 있는 게 특징**이다. 다른 값들은
전부 열별 합계다.

- **결과물1에서는 이 행을 그대로 둔다.** 4년째 써온 기존 양식이 이 합계행을
  포함하고 있어서, 형식을 그대로 유지하려면 이 행도 유지해야 한다.
- **결과물3에서는 이 행을 제외한다.** 이건 세금계산서를 요청할 "업체"가
  아니라 그냥 합계 숫자라서, 이 행으로 안내문구/표 블록을 만들면 존재하지
  않는 업체 앞으로 세금계산서 발행을 요청하는 이상한 메일 자료가 나온다.
  `generate_report3.py`는 사업자번호가 비어있는 행을 걸러내는 방식으로
  이걸 제외한다 (`load_report1`의 필터 참고).

## 결과물3 안내문구 커스터마이징

`generate_report3.py`의 `build_block()` 안, `notice_cell.value`에 들어가는
수식이 실제 이메일에 표시되는 안내문구를 결정한다. 지금은:

```
공급받는자 : 춘천지역먹거리직매장 (대표자 {대표자명})   /   {작성일자}자로 발행 해주세요.
```

형태로 되어 있다. 이건 사용자와 상의해서 정한 초안이니, 사용자가 문구를
바꿔달라고 하면 이 f-string만 고치면 58개(또는 매달 다른 개수) 업체
블록에 전부 한 번에 반영된다 — 블록마다 따로 고칠 필요 없다.

## 결과물3 검산 섹션

`write_check_section()`이 시트 상단(E5~E8)에 자동으로 채운다.

| 셀 | 내용 |
|---|---|
| E5 | 결과물3 안 모든 업체 소계의 매입금액을 다 더한 값 — `=H11+H18+...` 처럼 각 소계 행을 직접 더하는 수식 |
| E6 | 결과물1(전산원본) 합계행의 총지급예정액계 — 사용자가 스크립트 실행마다 다른 파일을 넣으므로 엑셀끼리 실시간으로 링크하지 않고, Python이 결과물1을 읽을 때 이 값을 그대로 적어 넣는다 |
| E7 | E5-E6 (차이) |
| E8 | `=IF(E7=0,"일치","불일치 - 확인 필요")`, 일치하면 초록/불일치하면 빨간 배경이 조건부 서식으로 자동으로 붙는다 |

이 섹션이 존재하는 이유: 결과물3은 결과물1에서 업체를 하나씩 순회하며
블록을 만드는데, 만약 필터링 로직을 잘못 고쳐서 업체가 하나 빠지거나
중복되면 총액이 어긋난다. 스크립트를 고칠 때마다 이 섹션이 "일치"로
나오는지 확인하면 실수를 바로 잡을 수 있다. **E6은 수식이 아니라
`load_report1()`이 계산해서 넣은 값**이므로, `load_report1()`의 합계행
필터 로직을 건드릴 땐 이 값도 같이 맞는지 확인한다.

### 색상

사용자가 복사·붙여넣기할 때 헷갈리지 않도록, 업체 블록의 열마다 다른
연한 파스텔 색을 준다 (`col_fill()` 참고) — 번호·업체명·구분은 연회색,
면세금액은 연녹색, 과세금액(공급가액·부가세·합계)은 연파랑, 매입금액은
연노랑. 헤더·데이터·소계 행 전부 같은 색 띠로 맞춘다. 색을 바꿔달라는
요청이 오면 `FILL_VENDOR`/`FILL_TAXFREE`/`FILL_TAXED`/`FILL_TOTAL` 네
상수만 고치면 전체에 반영된다.

## 출하내역서 스캔 파일명 자동 정리

하이포스에서 출하내역서(공급자별 매출 상세 내역서)를 자동 출력한 뒤 JPEG로
스캔한 파일들은, 파일명이 "1 (23).jpg" 처럼 순번뿐이라 어느 업체 것인지
알 수 없다. `rename_jpegs.py`는 각 이미지를 OCR로 읽어서 전산원본과
대조하고, 업체명으로 파일명을 바꾼 새 zip을 만든다.

```
python scripts/rename_jpegs.py <전산원본.xls> <출하내역서_스캔.zip> <결과.zip>
```

`--date`는 보통 생략한다. 출하내역서 상단에는 항상 "매출기간 :
2026년07월01일 ~ 2026년07월31일" 같은 문구가 찍혀 있는데, 스크립트가 이걸
OCR로 읽어서 종료일(예: 7월31일)을 작성일자로 자동 인식한다 — 스캔이
여러 장이면 다수결로 정하고, 실행 로그에 `작성일자 자동 감지: 7월 31일
(...)`로 근거를 찍는다. 자동 인식에 실패했을 때만(로그에 경고가 뜬다)
`--date "7월 31일"`처럼 직접 지정한다. 로그 맨 끝의 `작성일자(최종): 7월
31일`이 결과물3 생성(4번 단계)에 넘길 최종 값이다.

**의존성**: `tesseract` CLI를 직접 호출한다 (파이썬 바인딩 불필요) —
`apt-get install -y tesseract-ocr tesseract-ocr-kor` (한글 언어팩 필수).

### 파일명 규칙

메일에 zip 안 jpg를 첨부하면 그 **파일명이 메일 제목으로 그대로 쓰이기**
때문에, 다음 형식을 임의로 바꾸지 않는다:

```
{번호}. {월}월 {업체명} 매출내역 입니다.jpg
```

같은 업체의 출하내역서가 여러 장(품목이 많아 페이지가 나뉘었거나, 중복
스캔)이면 번호를 `9-1`, `9-2`처럼 세분화한다 — 번호(seq)는 전산원본에
나온 순서(=결과물3의 업체 번호)를 그대로 쓰고, 페이지 번호는 같은 업체로
확정된 파일이 나온 순서대로 1부터 매긴다 (`build_filename()` 참고). 확인
필요 파일은 이 형식을 강제하지 않고 `확인필요_` 접두사만 붙인다 — 아직
어느 업체인지 확신할 수 없는데 정식 번호를 매기면 오히려 위험하다.

### 매칭 규칙 (정확도가 최우선이라 임의로 느슨하게 바꾸지 말 것)

이름 OCR 하나만 믿지 않는다. 실제로 이름 OCR만으로 매칭했다가, 페이지
하단에 이름이 "영농조합법인"까지만 잘려서 전혀 다른 업체("꽃피는산꼴
영농조합법인")로 잘못 매칭된 사례가 있었다. 그래서 각 페이지에서 읽은
숫자들을 전산원본의 면세지급액·과세공급가액·부가세·과세지급액·
총지급예정액계·순매출금액·매출수수료와 대조해서, **3개 이상의 값이 한
업체와만 동시에 일치할 때만** 자동으로 이름을 바꾼다 (`classify()` 참고).
그렇지 않으면(항목이 1~2개뿐이거나, 여러 업체와 동점이거나, 아예 못
읽었으면) 파일명에 `확인필요_`를 붙이고 근거를 결과표에 남긴다 — 이
결과표를 사용자에게 같이 전달해서 빠르게 눈으로 훑을 수 있게 한다.

**업체명(핵심 상호) 텍스트 매칭 + 숫자-이름 상충 검사.** 처음엔 숫자
7항목만 셌는데, 그것만으로는 두 가지 문제가 있었다.

1. 업체명이 이미지 어딘가에(풋터 서명란뿐 아니라 **상품명 줄에도** —
   예: "매일봄" 브랜드 상품처럼) 그대로 적혀 있는데도 이걸 매칭 근거로
   안 써서, 숫자가 2개만 맞은 "주식회사매일봄"이 확정 문턱(3개)을 못
   넘고 확인 필요로 빠지는 경우가 있었다.
2. **더 심각하게**, 숫자만으로 우연히 3개 이상 겹치면 이름이 전혀 다른
   업체로 확정돼버리는 실제 사고가 있었다 — 정육업체 "로움에스"의
   스캔이 순전히 금액 우연 일치로 "스퀴즈"로 잘못 확정된 사례.

그래서 각 후보 업체마다 **"업체명(텍스트 언급)"도 하나의 매칭 항목으로
같이 센다** (`core_name()`/`coreName()` 참고 — "로움에스농업회사법인
유한회사(파파스컷)"처럼 법인 형태 표현과 괄호가 붙은 상호는 그걸 뗀
핵심 상호로 비교해야 실제로 텍스트에서 발견된다. "주식회사매일봄" →
"매일봄"). 그리고 **상충 검사**를 추가했다: 숫자만으로 3개 이상 맞은
1위 후보의 이름이 이미지 어디에도 안 보이는데, 다른 후보의 이름은
텍스트에서 발견됐다면 — 그건 숫자가 우연히 겹쳤다는 강한 신호이므로
확정하지 않고 확인 필요로 내린다(`classify()`의 `NAME_FIELD`/
`conflicting` 처리, JS는 `matchVendor`/`processZip`의 동일 로직 참고).
동점 상황에서도 이름까지 일치하는 후보가 단 하나면 그걸로 동점을
해소한다.

실제 데이터(60장)로 검증한 결과: 이 상충 검사를 넣기 전엔 "로움에스"
스캔 한 장이 "스퀴즈"로 잘못 확정됐었는데, 넣은 뒤로는 두 장 모두
"로움에스"로 정확히 7-1/7-2로 묶이고 "스퀴즈"도 정상적으로 1장만
남았다. "주식회사매일봄"도 이름 힌트 덕에 확인 필요에서 확정으로
올라갔다. 확정 수도 58→59장으로 늘었다(60장 중 1장은 스캔 자체가
너무 흐려서 여전히 확인 필요).

브라우저용 아티팩트(`settlement-tool/index.html`)에도 완전히 같은
알고리즘의 자바스크립트 버전이 있다 — 매칭 규칙, 작성일자 자동 인식
(`매출기간` 종료일 OCR) 둘 다 포함해서 동일하다. 웹 도구에서는
`dateInput`에 기본값("7월 31일")이 항상 채워져 있어서 "비어있으면
자동인식" 대신 "사용자가 필드를 직접 고친 적 있으면(=`dateManuallyEdited`)
그 값을 존중, 아니면 자동 인식"으로 판단한다. 규칙을 고칠 땐 두 구현이
갈라지지 않도록 양쪽(`scripts/rename_jpegs.py`,
`settlement-tool/index.html`) 다 고친다.

### 왜 웹 링크가 아니라 이 스킬(채팅)로 처리하는가

처음엔 브라우저에서 통째로 처리하는 웹 도구도 만들었지만, 실제로 써보니
이 방식이 더 낫다:
- 클로드 아티팩트의 파일 저장 기능은 `.xlsx`/`.zip` 확장자를 지원하지
  않는다 — 그래서 웹 도구는 결과물1을 CSV로, 결과물3을 HTML로, JPEG는
  파일 하나하나마다 저장 확인창을 띄우는 식으로 우회해야 했다.
- 이 스킬(채팅)에서는 `SendUserFile`로 진짜 `.xlsx`와 진짜 `.zip`을
  확인창 한 번으로 통째로 전달할 수 있다.
- 데스크톱 tesseract가 브라우저에 내장하기엔 너무 큰 고정밀 한글
  언어팩을 쓸 수 있어서, 실제로 인식률도 더 높다 (같은 60장 기준
  브라우저는 확정 50장, 이 스크립트는 확정 58장).

그래서 사용자가 특별히 "링크로 공유하고 싶다"고 하지 않는 이상, 기본은
이 스킬로 처리한다. 웹 도구는 클로드 계정이 없는 사람에게 링크만 공유하고
싶을 때만 대안으로 안내한다.

## 검증 방법 (수정할 때마다 확인)

이 환경에서는 LibreOffice 기반 수식 재계산(`recalc.py`)이 간헐적으로
작동하지 않을 수 있다. 그럴 땐 순수 파이썬 수식 평가 라이브러리로 대체
검증한다:

```bash
pip install -q formulas
python3 -c "
import formulas
m = formulas.ExcelModel().loads('결과물3_생성.xlsx').finish()
sol = m.calculate()
errors = [k for k,v in sol.items() if any(e in str(getattr(v,'value',v)) for e in ['#REF!','#NAME?','#VALUE!','#DIV/0!','#N/A','#NULL!','#NUM!'])]
print('formula errors:', len(errors))
"
```

`openpyxl`로 셀에 빈 문자열(`""`)을 쓰면 `<is>` 태그 없는 깨진
`inlineStr` 셀이 생겨 LibreOffice/Excel이 파일 자체를 못 여는 경우가
있었다 — 빈 칸은 아예 값을 쓰지 않고 비워둔다 (`ws.cell(...)` 자체를
호출하지 않음). 단일 셀에 `merge_cells`를 걸어도(범위가 셀 하나뿐인
병합) 같은 증상이 난다 — 병합은 항상 2개 이상의 셀 범위에만 사용한다.

## 매달 반복할 때

전산원본 파일만 새로 받으면 위 4~5단계 그대로 다시 실행하면 된다. 업체
수나 컬럼 구성이 크게 바뀌지 않는 한 스크립트 수정은 필요 없다. 하이포스
쪽에서 시트명이나 컬럼 순서를 바꿨다면 `generate_report1.py`의
`COLUMN_MAP`을 그에 맞게 고쳐야 한다.
